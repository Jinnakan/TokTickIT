# AI Use and Reflection — Lab 3

I used Claude Code (Claude Sonnet 5) as an AI coding assistant throughout
this sprint, across all nine Issues from the engineering contract through
release readiness. The working pattern stayed the same as Lab 2: every
Issue split into a "plan" turn (process and testing, covering both
software structure and security, no code touched) followed by a separate
"ready for feature N" turn that implemented, tested, and staged the work
for my own review before I committed. I reviewed every generated diff,
ran the real test suites and E2E specs myself (or had the assistant run
them and report the actual output), and treated the labsheet PDF and this
repo's own `docs/lab-03/*.md` as the authoritative source.

## My Reflection

**Specification-agent use.** I used Claude Code in a planning mode for Issue 13, before any implementation, and treated the sheet as the source of truth: I attached the PDF, asked for two planning passes (structure, then security), and asked for them to be merged. The strongest habit was giving the agent a vocabulary to work with, the design pattern list and the nine vulnerability classes, rather than asking for "a good spec". The weakness I found late is that the specification was only as complete as the checklist I checked it against. When I compared the finished app with the sheet during release readiness, two requirements had no owner in the specification: the Requester "Problem Appears Resolved" action (sheet sections 1, 4.4 BR-05 and 8.2) and realistic seed tickets with example comments and notes (section 5.3). Both looked covered in my head because the surrounding features existed, but no Acceptance Criterion or test pointed at them. A line-by-line traceability check of the sheet against `specification.md` during Issue 13, not just the other direction, would have caught both.

**Coding-agent use.** In implementation turns I worked in a fixed rhythm: plan turn, then "Ready for feature N", then I reviewed the staged diff and committed myself. The agent found real defects by exercising role boundaries, for example IT Staff getting 403 on Requester attachments (Issue 19) and a Requester still seeing only their own tickets when sending staff-only query parameters (Issue 18). The failures that cost the most time were in my tests, not the product: tests that assumed shared database state stayed unchanged (Issues 19 and 20). What worked was rerunning the full suite several times before trusting one green run. What I would change is the boundary of authority: the agent created a branch and assumed it could close Issues until I corrected it in Issue 20, and I should have stated that limit in the first prompt of the sprint. I also reviewed a collaborator's pull requests during the sprint, and the Administrator password finding from that review improved my own design more than any prompt I wrote myself.
