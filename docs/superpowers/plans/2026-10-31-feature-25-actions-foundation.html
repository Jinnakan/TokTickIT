Feature 25: Actions Taken foundation

Issue #48 · branch feature/25-actions-foundation into lab4-staging · server only (no UI, no workflow, no dashboards)

A. Read this

Goal. Give every Ticket a durable record of the work done on it. After this feature the API can create, list and edit Actions Taken with validation, assignee rules, a per-Action version, idempotent create, and a Ticket-row lock. The one additive database migration for the whole sprint lands here, including the status-history table and the Ticket version column that later Issues use.

Not in this feature. Transition matrix changes, resolution gate, expectedVersion on Ticket writes, appears-resolved, history endpoint, dashboards, any client code. Those are #49 to #52.

Decisions the plan makes (veto any of them before "Ready for feature 25").

  1. Pure rules live in packages/shared (action-rules.ts): validation, the status table, and the edit-lock verdict. The server service is thin and the Actions UI (#49) reuses the same functions. No database in the unit tests.
  2. The lock does the concurrency work. Every create/edit runs in one transaction that first does SELECT ... FOR UPDATE on the Ticket row (the pattern attachments.ts already uses). The Action version is then compared inside that lock and also in the UPDATE ... WHERE.
  3. Idempotency = lock + unique. A repeated requestId is looked up under the lock and returns the original (200). The (ticketId, requestId) unique index is the backstop.
  4. Ticket creation also writes its first history row now (api-spec §3 says so, and the table ships here). Otherwise Tickets created between #48 and #50 would have no history. This is the only change to Lab 2/3 route code besides the child-activity touch.
  5. Child activity touches Ticket.updatedAt (BR-L4-15) for Actions, and for Comments, Notes and Attachment upload/removal, through one touchTicket helper. Small, tested, and the dashboards need it.
  6. Demo seed becomes testable: logic moves to seed-demo-data.ts (runDemoSeed(client)), the script is a thin runner like seed.ts. Demo Actions are matched by a stable requestId so a re-run never overwrites a staff edit. One new demo Requester has no Tickets.
  7. Migration and seed tests run in a throwaway Postgres schema (CREATE SCHEMA mig_... and prisma migrate deploy against it), so they can insert legacy rows, apply the Lab 4 migration on top, run the rollback in a discarded transaction, and run the demo seed twice without touching the shared test data.
  8. Edge choices: an edit that changes nothing still bumps the Action version; switching followUpRequired off without sending a note clears the note and the done time; a repeated followUpDone: true keeps the first time.
