Feature 28: Dashboards and navigation

Issue #51 · branch feature/28-Role-dashboards from lab4-staging (needs features 25 to 27 merged) · server, client, E2E

A. Read this

Goal. Every role lands on a Dashboard that answers "what needs my attention?" in a few cards, and every card, count and row links into the detailed list or Ticket it summarizes. The numbers come from the database through small metric classes, are scoped by the session user, and always equal the rows their drill-down list returns.

What this feature also has to do. The drill-down needs two things that do not exist yet: the statusGroup and requesterReportedResolved list filters (WF-16, deferred from #50), and a way for a dashboard row to open a Ticket Detail directly and for Back to return to where you came from. Today each list screen keeps its own "open ticket" state, which cannot work from a dashboard. So navigation moves into one place.

Decisions the plan makes (veto any before "Ready for feature 28").

  1. Metric classes, one per number or list (Strategy pattern from the contract): each has compute(context); a small service runs them together and assembles the response. The service takes the Prisma client as an argument, so tests can run it against a throwaway schema.
  2. Clean-state and 300-ticket tests run in a throwaway Postgres schema (the sandbox from feature 25). The shared test database holds tens of thousands of Tickets from other tests, so "all zeros" (SD-04) and "about 300 Tickets under one second" (RD-08, SD-08) cannot be measured there. Counts that must equal direct queries (SD-01 and the rest) run against the shared database.
  3. "Recently resolved" uses history (feature 25's table): the Ticket is now Resolved or Closed and its latest move to Resolved is inside the last 7 days (UTC rolling window). A legacy Ticket is dated by its baseline row. A Ticket reopened later drops out because it is no longer Resolved or Closed.
  4. Administrator's users.byRole counts every user of that role (active and inactive), so the three role counts add up to active plus inactive. The contract's example numbers do not add up either way, so this is my reading; say if you want active-only.
  5. One navigation state, one reducer. A pure navReducer holds the current place (view plus filters), the open Ticket, and a refresh counter. List and dashboard screens stay mounted but hidden while a Ticket is open, so filters, page and typed search survive Back; the refresh counter makes them refetch on return so a changed status is not shown stale (the old queue never refetched).
  6. The Administrator gets the Ticket Queue (nav: Dashboard, Ticket Queue, User Management); Requester and IT Staff nav gain Dashboard first.
  7. A card is a real link (<a href> with one accessible name such as "Unassigned, 7 tickets") that opens the filtered list; "My open actions" is not a link and points down to its list, as the UI spec says.
  8. Existing E2E specs and client tests change on purpose: after login the first screen is the Dashboard, so specs that expect the queue or Users straight after login now click the nav item first.
  9. Out of scope here: the leftover health-check panel and other cleanup, the visual and accessibility sweep, and screenshots (hardening and release Issues).
