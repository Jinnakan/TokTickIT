Feature 27: Ticket workflow and resolution gate

Issue #50 · branch feature/27-Ticket-workflow-resolution-gate from lab4-staging · server and client · one E2E spec

A. Read this

Goal. Make the backend own the whole Ticket lifecycle. Status, priority and owner changes carry expectedVersion and run in one locked transaction; moving to Resolved is refused while the Actions say work is unfinished; every status change writes a history row; a Requester can say "this looks fixed" without changing the status. The staff screen then shows only the allowed next statuses, explains blockers in plain words, asks before cancelling, and lists history. This is the Issue that makes Actions Taken matter.

Already true, so not rebuilt. The transition matrix in ticket-state/* already equals BR-L4-09 (Lab 3 built the same table), so those classes stay; WF-U02 just proves it. Not in this feature: statusGroup and requesterReportedResolved list filters (WF-16, they exist for dashboard drill-down, so they belong to #51), dashboards, navigation.

Decisions the plan makes (veto any before "Ready for feature 27").

  1. A facade, not scattered routes. ticket-workflow-service.ts is the single entry point for claim, reassign, priority, status and appears-resolved. Each write: lock the Ticket row, 404 if missing, compare expectedVersion, check the transition (State classes), run the resolution gate for Resolved, update, append history, apply side effects, all in one transaction. The old staff-ticket-actions.ts is replaced by a thin ticket-workflow-router.ts.
  2. Check order inside a status change: 400 (missing or bad expectedVersion, bad body) → 404 → 409 STALE_UPDATE → 409 INVALID_TRANSITION → 409 RESOLUTION_BLOCKED → write. Stale comes first because a changed version means the state you judged the move against may be gone. (api-spec lists the same four 409s without ordering.)
  3. The gate is a pure function (resolution-gate.ts) fed with Action facts, unit-tested over every combination (WF-U01). The same function builds the resolution block on GET /api/tickets/:id, so the UI explains a blocker without reimplementing the rule.
  4. Lab 3 tests must change, on purpose. They call these routes without expectedVersion (now 400) and resolve Tickets with no Completed Action (now blocked). I update them to send the version and to add a Completed Action first, and say so in the commit, rather than weakening the new rules.
  5. The lock test is deterministic. A test transaction holds the Ticket row lock, a Resolve request is fired, the test proves it waits, adds a Planned Action inside the lock, commits, and the Resolve must then fail with ACTIONS_STILL_OPEN. A racing-requests loop cannot show that, because "resolve then add" is also a valid result.
  6. The staff screen stops flashing "Loading ticket…" on refresh. First load still shows it; later refreshes (after a status change, or an Action change, which feature 26 deferred to here) keep the page and swap data in. Without this, saving an Action would destroy the open Action form. The Actions list and History refetch quietly when ticket.version changes, because a Cancel changes Actions on the server.
  7. Cancel asks first in an inline role="alertdialog" that names what will happen to open Actions, the same pattern as Cancel action.
  8. History creation row already exists (feature 25); this feature writes one row per status change, and only status changes (BR-L4-16).
