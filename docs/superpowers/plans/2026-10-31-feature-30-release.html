The order matters. The handout asks for evidence "from main", for rendered documents, and for commit history showing feature branches merged into lab4-staging and then main. Most of that can only exist after the release merge. So the work has two halves:

  1. In the repository (this feature, before the release PR): verification script, screenshots, evidence scripts, reviewer.md, ai-use.md, final checks.
  2. After the release merge (yours, then mine): the GitHub steps only you can do, then capture of the GitHub pages and test output from main, then the report.

Decisions the plan makes (veto any before "Ready for feature 30").

  1. Screenshots come from a repeatable capture script (a Playwright run you start on demand, kept out of the normal test run). It creates its own Tickets and Actions through the real API, and uses a mocked response only for states live data cannot show: loading, failure, and an empty staff dashboard. Every mocked shot is marked as such in an index file, so nothing is passed off as live.
  2. About 70 images: the contract's 54 (staff dashboard 5 states, requester dashboard 4, Actions Taken 9, each at 1280, 768 and 390 px) plus 16 regression screens (8 Lab 1 to 3 screens at desktop and mobile) for Part 8. Expected size 8 to 15 MB, like Lab 3's 15 MB. The repository keeps every image; the report does not: Task 9 builds one contact sheet per scene (the three widths side by side, Pillow) so the PDF carries about 25 pictures, not 70, and test output is excerpted per file with counts, not pasted line by line.
  3. A release verification script (npm run verify:release) that checks every file the handout lists exists, no test row is Planned, no checklist box is open, every screenshot in the index exists, and the ignore rules hold. The report is not started until it passes.
  4. reviewer.md is built from GitHub data, not memory. I read the real reviews and comments with gh (read only) and quote them. The history is stated honestly: the first attempt's PRs #54 to #57 were reset; PR #59 was merged without a formal approval; PR #64 and the release PR are filled in only after they exist.
  5. ai-use.md quotes your real prompts taken verbatim from this project's session transcript (6 to 10 chosen). I draft the reflection in first person from what actually happened, and you edit it: it is your reflection and your grade.
  6. The AI planning reviews count as evidence. Each plan was reviewed by a fresh read-only agent, and those reviews caught real defects before any code was written (for example a test that could never fail, a hidden-list bug, a build-breaking import rewrite). reviewer.md lists them next to the human reviews, clearly labelled.
  7. The report is a Word file built by script in your Lab 3 style (plain bold part headings, "Image N : caption", no Word heading styles, no em dashes), with images embedded and links live. You export the PDF from Word (Save As PDF); the only images I cannot produce are the Kanban board and anything behind a login, which the plan lists for you.
  8. Merges, the release PR and the Kanban are yours, as before; the plan gives the exact sequence and the checks to run after each step.
