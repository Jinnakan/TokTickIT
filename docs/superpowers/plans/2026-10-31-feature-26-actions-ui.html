Feature 26: Actions Taken UI

Issue #49 · branch feature/26-... from feature 25 · client + one E2E spec · no server changes

A. Read this

Goal. Put the Actions Taken API from feature 25 on screen. IT Staff and Administrators see a list of Action cards on Ticket Detail, add an Action, edit one, and use Start, Complete, Cancel and Mark-follow-up-done. Requesters see the same cards read-only. Everything from ui-spec.md §4 (list, create/edit form, feedback states) and §7 (Action badge) lands here.

Not in this feature. Status-workflow controls, blocker panel, history list, "Problem appears resolved", dashboards, navigation changes. Those are #50 and #51.

Decisions the plan makes (veto before "Ready for feature 26").

  1. One panel owns its own data. ActionsTakenPanel fetches and holds the Action list. A save updates that list in place and announces "Action saved". It does not reload the whole Ticket, because the existing reload (claim, status) replaces the page with "Loading ticket…" and would throw away an open form. The Mediator gets a new onActionChanged in #50, when the Ticket summary needs the resolution blockers.
  2. Validation is shared, not copied. The form builds the same request body it will send, runs it through parseActionBody from @toktickit/shared (feature 25), and shows those messages under the fields. The server stays the authority; the client just gets the same wording before a round trip.
  3. Pure form logic is separate from React (action-form.ts: initial values, allowed statuses, locked fields, payload builder, validation). It is unit-tested without rendering.
  4. Double submit is blocked by a ref, not only by disabled state. State updates are async, so two fast clicks could both pass a state check. A useRef flag is set synchronously.
  5. One requestId per opened form (act-<uuid>), kept across retries, so a network retry cannot create a duplicate.
  6. Stale edit keeps the user's text. The 409 message has a Reload button that refetches the list and re-bases the form on the fresh version; typed values stay.
  7. Complete is a shortcut into the edit form with status preset to Completed and focus on Result (a Result is required, so one click cannot complete blindly). Start and Cancel action send one PATCH directly; Cancel asks first in an inline role="alertdialog".
  8. Locked Ticket (Closed or Cancelled): staff see the sentence "This ticket is closed, so actions can no longer be changed." instead of Add and Edit.
  9. Placement: the panel sits right after Service Actions, so it is between Service Actions and Comments as the UI spec says; Attachments follow it.
  10. Existing test stubs get the new URL. Several Lab 2/3/4 tests stub fetch with a fixed URL list that throws on anything else; they need /api/tickets/42/actions.
