# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a Requester-facing IT ticketing MVP: a temporary Development Requester
selector standing in for login, a Create Ticket flow with attachment upload,
a searchable/sortable/paginated My Tickets list, and a read-only Ticket Detail
screen where a Requester can inspect and manage their own attachments — all
on a consistent Zen Green UI foundation that later sprints will reuse.

## 2. Stakeholder Request Interpretation

The IT department wants Requesters to self-serve support tickets before real
login exists. A Requester must be able to pick a test identity, describe a
problem with category/related system/priority/evidence, submit it and get a
Ticket Number back, then find that ticket again, inspect it, and add or
remove attachments — while never seeing another Requester's tickets. Ticket
workflow (status changes, IT Staff assignment, comments) is deliberately
deferred to a later sprint.

## 3. Scope

### Included

- Development Requester Selection screen (fake "login") and Change Requester
- Create Ticket: form, validation, attachment upload at submission time
- My Tickets: search, filter, sort, pagination, list/card UI
- Requester Ticket Detail: read-only ticket fields
- Attachment lifecycle on an existing ticket: add, download, soft-remove
- Ownership enforcement (a Requester can only reach their own tickets/attachments)
- Zen Green UI foundation (colors, form/list/badge/loading/empty/error states, responsive rules)
- Category / Related System / Development Requester seed data

### Excluded

- Real authentication, password/session/token handling, role-based authorization
- IT Staff dashboard, queue, claiming, reassignment, IT Priority
- Public Comments, Internal Notes, Actions Taken
- Any status transition beyond the initial `NEW` status (resolving, closing, reopening, cancelling)
- Administrator functions (user/role/reference-data management)

## 4. Functional Requirements

- **FR-01** The system shall let a user select one active Development
  Requester from a list before any ticket screen is reachable.
- **FR-02** The system shall let the selected Requester change identity at
  any time via a Change Requester action, reloading Requester-scoped data.
- **FR-03** The system shall let the selected Requester create a Ticket by
  supplying Category, Related System, Requested Priority, Summary, and
  Description, and optionally attaching files.
- **FR-04** The system shall generate a unique, backend-assigned Ticket
  Number and return it on successful creation.
- **FR-05** The system shall let the selected Requester retrieve a paginated,
  searchable, filterable, sortable list of only their own Tickets.
- **FR-06** The system shall let the selected Requester open a Ticket Detail
  screen for a Ticket they own, showing all ticket fields as read-only.
- **FR-07** The system shall let the selected Requester add a permitted
  Attachment to an existing Ticket they own.
- **FR-08** The system shall let the selected Requester download an active
  (not removed) Attachment on a Ticket they own.
- **FR-09** The system shall let the selected Requester soft-remove an
  Attachment they own, requiring a removal reason.
- **FR-10** The system shall reject any attempt to view, list, or modify a
  Ticket or Attachment that does not belong to the selected Requester.
- **FR-11** The system shall show clear loading, empty, no-results, and
  failure states on every Requester-facing screen.

## 5. Business Rules

| BR ID | Rule |
|---|---|
| BR-01 | The official Ticket Number is generated by the backend and must be unique. |
| BR-02 | A new Ticket begins with Current Status `NEW`. |
| BR-03 | Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication. |
| BR-04 | Ticket Number format is `TKT-{creationYear}-{ticketId zero-padded to 6 digits}`, derived from the Ticket's own database id, guaranteeing uniqueness without a separate counter. |
| BR-05 | Ticket Date, Ticket Number, Requester, and Current Status are system-generated/read-only and are never accepted from client input. |
| BR-06 | Ticket Summary is required, trimmed, and must be 5–150 characters. |
| BR-07 | Ticket Description is required, trimmed, and must be 10–2000 characters. |
| BR-08 | Category and Related System are required and must reference an existing **active** record; inactive or unknown ids are rejected. |
| BR-09 | Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`; no default is pre-selected. |
| BR-10 | A Ticket is always owned by exactly the Development Requester selected at creation time (`requesterId` on the Ticket); ownership never changes in Lab 2. |
| BR-11 | Only active Development Requesters appear in the Requester selector; an inactive Requester cannot be selected and any stored selection referencing an inactive/unknown Requester is treated as no selection. |
| BR-12 | The My Tickets list only ever returns Tickets owned by the currently selected Requester; this is enforced server-side, not just hidden in the UI. |
| BR-13 | Ticket search matches Ticket Number or Summary, case-insensitive, partial match. |
| BR-14 | Ticket list default sort is Created Date descending, with Ticket id descending as a stable secondary sort. |
| BR-15 | Ticket list pagination defaults to page 1, page size 10; requested page size is clamped to the range 1–50. |
| BR-16 | Allowed Attachment types are JPG/JPEG, PNG, WEBP, and PDF, validated by both file extension and declared MIME type. |
| BR-17 | Maximum Attachment size is 5 MB per file. |
| BR-18 | A Ticket may have at most 5 **active** Attachments; soft-removed Attachments do not count toward this limit. |
| BR-19 | Attachment removal is soft: the row is flagged removed with a timestamp and a required reason (3–200 characters); files are never hard-deleted in Lab 2. |
| BR-20 | A removed Attachment's metadata (filename, size, uploaded date, removed date, removed reason) remains visible on the Ticket, but the file itself cannot be downloaded or previewed. |
| BR-21 | If Ticket creation succeeds but one or more attachment uploads fail, the Ticket is still created and returned with its Ticket Number; failed attachments are not retried automatically and must be added again from Ticket Detail (compensating action, not a rolled-back transaction). |
| BR-22 | Every Requester-scoped API request must include the selected Development Requester's id via the `X-Dev-Requester-Id` header; a missing, unknown, or inactive id is rejected before any ownership check runs. |
| BR-23 | In Lab 3, the Development Requester selector and the `X-Dev-Requester-Id` header are replaced by real authenticated sessions; the Ticket/Attachment ownership model (`requesterId` foreign key) does not need to change, only how the current requester is established.

## 6. UI Specification Summary

Full detail lives in `ui-spec.md`. Summary:

- **Application shell**: TokTickIT header, My Tickets / Create Ticket nav, current Requester name + Change Requester, active-page indication, responsive nav.
- **Development Requester Selection**: dropdown of active Requesters, loading/empty/API-failure states, Continue button, Lab-2-only disclaimer.
- **Create Ticket**: system-generated fields visually distinct and non-editable; classification fields grouped; Summary/Description given width; Attachments below main fields; primary Submit + secondary Cancel; field-level validation messages; busy Submit state; success state showing the generated Ticket Number.
- **My Tickets**: search box, Category/Requested Priority/Current Status filters, sortable columns, pagination, Create Ticket action, desktop table / mobile card layout, loading/empty/no-results/failure states.
- **Requester Ticket Detail**: read-only field grid plus an Attachments section (add, download, soft-remove with reason); no comments/notes/actions/status controls.
- All screens follow the Zen Green color tokens, field-state rules, and responsive breakpoints defined in `ui-spec.md`.

## 7. Data Changes

New Prisma models (full field list, indexes, and migration notes in the
schema itself and `api-spec.md`):

- **DevRequester** — `id`, `name`, `email` (unique), `isActive` (default `true`), `createdAt`.
- **RelatedSystem** — `id`, `name` (unique), `isActive` (default `true`), `createdAt`.
- **Category** (existing model, extended) — add `isActive` (default `true`) so inactive categories can be retired without deleting history.
- **Ticket** — `id`, `ticketNumber` (unique, backend-generated post-create), `requesterId` (FK → DevRequester), `categoryId` (FK → Category), `relatedSystemId` (FK → RelatedSystem), `summary`, `description`, `requestedPriority` (enum `Priority`), `currentStatus` (enum `TicketStatus`, default `NEW`), `createdAt`, `updatedAt`.
- **Attachment** — `id`, `ticketId` (FK → Ticket), `originalFilename`, `storedPath`, `mimeType`, `sizeBytes`, `uploadedAt`, `isRemoved` (default `false`), `removedAt` (nullable), `removedReason` (nullable).
- **enum Priority** — `LOW`, `MEDIUM`, `HIGH`.
- **enum TicketStatus** — `NEW` only in Lab 2; the enum type exists so Lab 3 can extend it via migration without changing the column type.

`ticketOwner` (IT Staff assignment) and `itPriority` are intentionally not
added yet — they belong to the excluded IT Staff workflow (see §3, §11).

## 8. API Contract

Full request/response shapes, statuses, and error cases are in
`api-spec.md`. Endpoints required for this sprint:

- `GET /api/categories` (active only) — existing endpoint, add `isActive` filter
- `GET /api/related-systems` (active only)
- `GET /api/dev-requesters` (active only)
- `POST /api/tickets`
- `GET /api/tickets` (paginated, searchable, filterable, sortable; scoped to `X-Dev-Requester-Id`)
- `GET /api/tickets/:id` (scoped to `X-Dev-Requester-Id`)
- `POST /api/tickets/:id/attachments`
- `GET /api/tickets/:id/attachments` (metadata list, including removed)
- `GET /api/attachments/:id/download` (active only)
- `DELETE /api/attachments/:id` (soft-remove, requires `reason` in body)

## 9. Acceptance Criteria

| AC ID | Criterion |
|---|---|
| AC-01 | Given valid Ticket data, when the Requester submits the Create Ticket form, then one Ticket is saved and the official Ticket Number is displayed. |
| AC-02 | Given no Development Requester is selected, when the user attempts to open My Tickets, Create Ticket, or Ticket Detail, then the Requester Selection screen is shown instead. |
| AC-03 | Given Requester B is selected, when a Ticket belonging to Requester A is requested (list or detail), then Requester A's Ticket data is not returned. |
| AC-04 | Given the Create Ticket form is submitted without a Summary, when validation runs, then a field-level message appears next to Summary and no API call is made. |
| AC-05 | Given the Create Ticket form is submitted with a Summary shorter than 5 characters or longer than 150, then a field-level length message appears and no API call is made. |
| AC-06 | Given a Category id that is inactive or does not exist, when Ticket creation is attempted, then the API returns 400 with a field-level error and no Ticket is created. |
| AC-07 | Given a valid Ticket is created with two valid attachments and one oversized attachment, when submission completes, then the Ticket and the two valid Attachments are saved, and the UI reports the failed attachment by name with a retry path from Ticket Detail. |
| AC-08 | Given a Ticket has 5 active Attachments, when a 6th Attachment is added, then the API rejects the upload with 400 and no Attachment is created. |
| AC-09 | Given an Attachment of a disallowed type (e.g. `.exe`) is selected, when upload is attempted, then the client blocks submission and shows a type error without calling the API. |
| AC-10 | Given a Requester searches My Tickets by partial Ticket Number, when the query matches zero Tickets, then a no-results state is shown (distinct from the empty-list state for a Requester with zero Tickets total). |
| AC-11 | Given a Requester has more than one page of Tickets, when they page forward, then the correct next page of their own Tickets is shown and the URL/query state reflects the page. |
| AC-12 | Given a Requester opens Ticket Detail for their own Ticket, when the page loads, then all Ticket fields render as read-only and no comment/notes/status controls are present. |
| AC-13 | Given a Requester removes an Attachment with a valid reason, when removal completes, then the Attachment shows as removed with its metadata still visible, its download control is disabled, and `GET /api/attachments/:id/download` returns 410 for it. |
| AC-14 | Given a Requester removes an Attachment without supplying a reason, when they submit, then the removal is blocked client-side and the API rejects a reason-less request with 400. |
| AC-15 | Given the Development Requester API call fails, when the Requester Selection screen loads, then a safe failure state is shown instead of a blank or crashed screen. |
| AC-16 | Given zero active Development Requesters exist, when the Requester Selection screen loads, then an empty state explains no Requesters are available instead of showing an empty dropdown silently. |
| AC-17 | Given a Requester is on a screen at desktop, tablet, and mobile viewport widths, when the layout renders, then no labels are clipped, no controls overlap, and the page never scrolls horizontally. |
| AC-18 | Given the backend is unreachable, when My Tickets attempts to load, then a failure state with retry is shown and stale/partial data is not presented as current.

## 11. Assumptions and Decisions

- **Requester context transport**: the selected Development Requester id is sent as an `X-Dev-Requester-Id` request header (not a query parameter) on every Requester-scoped endpoint, so the pattern mirrors how an `Authorization` header will work once Lab 3 introduces real auth (BR-22, BR-23).
- **Attachment storage**: files are stored on the server's local filesystem under a per-ticket directory with a generated (non-guessable) filename; only metadata is stored in Postgres. This is sufficient for course scope; object storage is out of scope.
- **Attachment upload timing**: attachments are uploaded in a second step after the Ticket itself is created (ticket creation and each attachment upload are separate API calls), which is what makes the compensating-action behavior in BR-21 possible instead of requiring a multi-file atomic transaction.
- **Cross-requester access status code**: requesting a Ticket or Attachment that doesn't exist returns `404 Not Found`; requesting one that exists but belongs to a different Requester returns `403 Forbidden`. This is easier to debug during development than a uniform 404, at the cost of confirming an id exists to a Requester who can't access it — acceptable for this course's threat model.
- **Missing/invalid Requester context status code**: a missing, unknown, or inactive `X-Dev-Requester-Id` returns `400 Bad Request` (not `401`), since BR-03 explicitly treats the selector as a non-authentication testing mechanism.
- **No default Requested Priority**: the field starts unselected so a Requester makes an explicit choice, matching the required-field/asterisk rule in `ui-spec.md`.
- `ticketOwner`/`itPriority`/status-transition fields are deferred to Lab 3 rather than added now and left unused (YAGNI); §7 documents that the enum/model shapes chosen here don't block that extension.
